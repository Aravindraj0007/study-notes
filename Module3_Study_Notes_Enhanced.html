Stage 3.1 — Data Warehouse Architectures

Cloud Data Warehouse Architectures — key features

Recap from Module 1: A data warehouse is a database purpose-built for analysis (OLAP) — fast on big scanning queries, not on quick individual transactions like an app's checkout.

OLTP vs OLAP — the distinction the whole module rests on:

OLTP (RDS, Module 1)OLAP (Warehouse, this module)
PurposeRun the business (place an order)Analyze the business (total sales trend)
Typical query"Insert this one order""Sum revenue across 3 years, grouped by region"
Query touchesA few rowsMillions of rows, few columns
Storage layoutRow-based (fetch a whole record fast)Column-based (scan one field across everything fast)
Optimized forMany small, fast writesFew large, heavy reads

This is the single most exam-relevant distinction in the module — almost every other concept below exists because OLAP has this different access pattern from OLTP.

Key architectural features that make OLAP fast:

  • Columnar storage — same concept from Module 2 (Parquet/ORC). The warehouse stores data column-by-column internally, so scanning "just the sales column across 10 million rows" is fast. This is why a warehouse can answer in seconds what would take an OLTP database minutes or longer.
  • Massively Parallel Processing (MPP) — the warehouse splits a big query across many machines/nodes at once, each working on a slice of the data, then combines results. This is the same "split the work, then combine" idea as MapReduce from Module 1, just built directly into the database engine rather than being a separate framework you invoke.
  • Compute/storage separation (its own point below) — the warehouse can scale its processing power independently of how much data it's storing.

Easy example: Imagine 50 people each checking a different shelf in a warehouse for a product, instead of 1 person walking the entire warehouse alone — that's MPP. The warehouse finds your answer fast because it divides the search.

Why MPP specifically needs columnar storage to be effective: if the data were row-based, each node would still have to read entire rows (including columns nobody asked for) before discarding the unneeded parts — wasting the parallelism. Columnar storage means each node only pulls the relevant column slice for its shard, so the parallel work is actually proportional to what's needed, not the whole record width. The two features compound each other rather than being independent tricks.

Redshift (AWS)

  • AWS's data warehouse service. You provision a cluster (a set of machines) sized for your workload, and it stays running (and billing) until you resize/pause it.
  • Internally organized as a leader node (receives the query, plans how to split it, combines final results) and multiple compute nodes (each holds a slice of the data and does the actual scanning) — this is the concrete machinery behind the "50 people checking shelves" MPP example above.
  • Easy example: Like renting a fixed-size team of workers who are always on standby, ready to answer any question about your data instantly — but you pay for them whether they're busy or idle.

Synapse (Azure)

  • Azure's equivalent — combines data warehousing and big data analytics (Spark) in one service. Conceptually does the same job as Redshift, Microsoft ecosystem.
  • Distinguishing detail worth remembering: Synapse deliberately blends the provisioned warehouse model (like Redshift) and the serverless query model (like Athena, see Stage 3.3) under one product umbrella — Redshift and Athena are two separate AWS services, but Synapse offers both modes within itself.

BigQuery (GCP)

  • Google's data warehouse — but architecturally different in one important way: it's serverless by default. You don't provision a cluster; you just run a query and pay for the data scanned. (This blurs into the "serverless querying" idea in Stage 3.3 — BigQuery does both jobs.)
  • Conceptual reason this matters: Redshift asks "how big a team do I keep on standby?" (capacity-planning problem). BigQuery removes that question entirely — there's no cluster to size, only a query to run. This is the same trade-off pattern you saw with EC2 (provisioned) vs. Lambda (serverless) in Module 1/4, just applied to the warehouse layer.

Compute/storage separation concept

The old way (traditional databases): compute (processing power) and storage (where data sits) were bundled together on the same physical machine. Want more storage? You had to buy more compute too, even if you didn't need it.

The cloud warehouse way: compute and storage are separate services that scale independently.

Easy example: Imagine a restaurant where the kitchen (compute) and the food storage fridge (storage) used to have to be the same size, bolted together. Cloud warehouses let you have a huge fridge (lots of cheap storage) with a small kitchen (little compute) most of the time, and temporarily hire more chefs (scale up compute) only when a big order comes in — without touching the fridge at all.

Why it matters: You can store years of historical data cheaply, and only pay extra compute when you actually run a big analytical query on it. This is also the architectural reason serverless querying (Stage 3.3) is even possible — once storage and compute are decoupled, "compute" can shrink all the way down to "pay only for the seconds a single query runs," which is exactly what Athena/BigQuery do.

Stage 3.2 — Data Loading and SQL

Data Loading and Management — best practices

Getting data into a warehouse efficiently matters as much as querying it. Key practices:

  • Bulk loading over row-by-row inserts — loading a million rows one at a time is painfully slow; warehouses are built to ingest large batches/files at once (e.g., loading a Parquet file directly from S3). The reason row-by-row is so much worse isn't just "more commands" — each individual INSERT typically triggers its own transaction overhead, logging, and index updates, all of which get amortized across the whole batch when you bulk-load instead.
  • Load during off-peak hours where possible, so loading doesn't compete with users running queries — loading is itself a compute-heavy operation on the same cluster, so it directly steals MPP capacity from anyone querying at the same time.
  • Validate data before loading — catching bad data at the source is cheaper than cleaning it after it's sitting in the warehouse. This connects directly to the "veracity" idea from Module 1's 5 Vs — validation is the concrete mechanism that protects veracity at load time.

Distribution and partitioning strategies

Partitioning — splitting a huge table into smaller chunks based on a column, usually date (e.g., one partition per day/month). When you query "sales in March," the warehouse only scans the March partition, not the entire table.

Distribution — deciding how data is spread across the multiple machines in the warehouse cluster (relevant for MPP systems like Redshift). Data related to the same query (e.g., a customer's orders) is ideally kept on the same machine, so the warehouse doesn't need to shuffle data between machines mid-query.

The distinction that's easy to blur (exam favorite): partitioning is about skipping irrelevant data before scanning even starts; distribution is about arranging data across nodes so that, once scanning does start, the nodes don't have to talk to each other more than necessary. One reduces how much you read; the other reduces how much the nodes communicate. A well-designed warehouse table gets both right independently — you can partition well but distribute badly (nodes still shuffle data constantly), or vice versa.

Easy example — partitioning: Like organizing a library by year of publication instead of one giant unsorted pile. Looking for a 2023 book? Go straight to the 2023 shelf, ignore the rest.

Easy example — distribution: Like assigning each of the 50 warehouse workers (from the MPP example) a specific, logically grouped set of shelves, so a worker rarely needs to walk over and ask another worker for something.

Common distribution strategies (conceptual, not memorization-heavy, but good to recognize by name):

  • Even/Round-robin distribution — rows spread evenly across nodes with no particular logic; simple, but unrelated data ends up scattered, so joins often require shuffling.
  • Key-based distribution — rows distributed based on a specific column's value (e.g., customer_id), so all of one customer's rows land on the same node — ideal when queries frequently join or group by that column.
  • All/Broadcast distribution — a full copy of a (usually small) table is kept on every node, so it never needs to be shuffled when joined against larger, distributed tables.

SQL for Cloud Warehouses — advanced SQL concepts

Beyond basic SELECT/WHERE, warehouse work leans on:

  • Aggregations — SUM, AVG, COUNT, GROUP BY (e.g., "total sales per region")
  • Window functions — calculations across a set of rows related to the current row without collapsing them into one result (e.g., "running total of sales by day," "rank each product by revenue within its category"). The key conceptual difference from GROUP BY: GROUP BY reduces N rows down to fewer summary rows; a window function keeps all N rows but adds a calculated column alongside each one.
  • JOINs across large tables — combining data from multiple tables (e.g., orders + customers + products), which is where partitioning/distribution choices really affect speed — a join between two tables distributed on the same key can happen entirely locally on each node; a join between mismatched distribution keys forces the cluster to shuffle rows between nodes first, which is much slower.

Performance tuning basics

  • Query only the columns you need (SELECT specific_columns, not SELECT *) — matters more in columnar warehouses since it directly controls how much data gets scanned.
  • Filter early using partitioned columns (like date) so the warehouse skips irrelevant data before doing heavier work.
  • Avoid unnecessary complex joins on huge unfiltered tables — filter first, join second where possible. The underlying principle tying all three together: reduce the amount of data the engine touches as early as possible in the query plan — every optimization here is really the same idea applied at a different stage (column selection, row selection, join order).

Stage 3.3 — Serverless Querying

The core idea

Serverless querying = run SQL directly on data sitting in a data lake (S3), without loading it into a warehouse or managing any cluster at all. You pay per query (usually based on how much data it scans), not for a warehouse sitting idle 24/7.

Easy example: Instead of hiring a permanent full-time team (a provisioned warehouse) to always be ready for questions, you call in a freelancer only when you have a question, pay them just for that one task, and they leave when done.

Why this is only possible because of compute/storage separation (Stage 3.1): once storage (S3, the lake) is fully decoupled from compute, there's no architectural requirement that "compute" be a standing cluster at all — it can be a transient process spun up for the duration of one query and destroyed immediately after. Serverless querying is compute/storage separation taken to its logical extreme.

Athena (AWS)

  • Runs standard SQL queries directly against files (like Parquet/CSV) sitting in S3.
  • This is where Stage 2.3's storage formats directly matter: an Athena query on Parquet data is dramatically cheaper and faster than the same query on raw CSV, because Athena bills by data scanned — and columnar formats mean scanning less.
  • Athena relies on the Glue Data Catalog (Module 2) to know what tables/columns exist in your S3 data in the first place — without a catalog entry, Athena has no schema to query against. This is the direct link between Module 2's crawler work and being able to run a single SQL query in Module 3.

Synapse Serverless (Azure)

  • Azure's equivalent to Athena — query data lake files directly with SQL, no cluster to manage, pay per query.

BigQuery (GCP)

  • As mentioned in 3.1, BigQuery already works this way by default — it's simultaneously "the warehouse" and "the serverless query engine" for GCP, which is why it doesn't have a clearly separate name like Athena/Synapse Serverless. Conceptually, think of AWS and Azure as offering two distinct products (a provisioned warehouse + a separate serverless query tool) while GCP collapses both roles into one product that behaves serverlessly regardless of which "mode" you think you're using.

Analyzing query performance and cost

The two are directly linked in serverless tools: more data scanned = slower AND more expensive. This connects everything from earlier stages into one practical skill:

  • Using Parquet instead of CSV → less data scanned → cheaper + faster
  • Using partitioned data (e.g., folder-per-date in S3) → the query engine skips irrelevant partitions entirely
  • Selecting only needed columns → columnar formats let the engine skip unused columns physically on disk

Quick comparison — Warehouse vs Serverless Query:

Provisioned Warehouse (Redshift)Serverless Query (Athena)
SetupCluster must be runningNo setup, query directly
BillingPay for cluster uptimePay per query (data scanned)
Best forFrequent, heavy, predictable workloadsOccasional or exploratory queries
Data locationLoaded into the warehouseStays in the data lake (S3)

The underlying economic logic (this is the part exams like to probe as an "evaluate/analyze" question, per Module 5.4's Bloom's-level framing): a provisioned cluster has a fixed cost regardless of usage — cheap per-query only if you run enough queries to amortize that fixed cost. Serverless has zero fixed cost but a per-query cost — cheap overall only if query volume stays low. There's a theoretical break-even query volume above which provisioned becomes cheaper than serverless; the exact number depends on cluster size and data volume, but the shape of that trade-off (fixed cost vs. variable cost) is the concept to know, not a specific number.

Stage 3.4 — Practical Component

Quick reference — what you should be able to do (see the full walkthroughs in your hands-on lab material; theory takeaways above are the priority for this pass):

  • [ ] Set up a cloud data warehouse — launch a small Redshift cluster (or equivalent) on a free/trial tier
  • [ ] Apply data loading techniques — bulk-load a CSV or Parquet file from S3 into the warehouse
  • [ ] Run analytical SQL queries — practice GROUP BY, aggregations, and at least one window function
  • [ ] Compare performance across approaches — run the same query on raw CSV vs. Parquet, or on partitioned vs. unpartitioned data, and note the time/cost difference
  • [ ] Apply serverless querying on a data lake — run an Athena (or Synapse Serverless) query directly on S3 data without loading it anywhere
  • [ ] Use a graphical ETL tool to clean a dataset — e.g., AWS Glue Studio's visual interface to clean/transform a dataset before analysis

1. What is MPP, and how does it relate to MapReduce from Module 1? > MPP (Massively Parallel Processing) splits a query across many machines/nodes at once, each processing a slice of the data, then combines the results — the same "split, process, combine" idea as MapReduce, except it's built directly into the warehouse engine rather than being a separate framework you run manually.

2. What does "compute/storage separation" mean, and why does it save money? > Compute (processing power) and storage (where data lives) are separate, independently-scaling services instead of being bundled on the same machine. It saves money because you can store large volumes of data cheaply while only paying extra for compute during the moments you actually run heavy queries — you're not forced to buy more processing power just because you need more storage, or vice versa.

3. What's the difference between partitioning and distribution? > Partitioning splits a table into chunks based on a column (usually date) so queries can skip irrelevant chunks entirely before scanning — it reduces how much data is read. Distribution decides how data is spread across the multiple machines in an MPP cluster so related data sits together — it reduces how much nodes have to communicate/shuffle data during a query.

4. What is serverless querying, and how is its billing different from a provisioned warehouse? > Serverless querying runs SQL directly on data sitting in a data lake (e.g., S3) without provisioning or managing any cluster. Billing is per-query, based on how much data the query scans — versus a provisioned warehouse, which bills for cluster uptime regardless of whether it's actively being queried.

5. Why does querying Parquet data via Athena cost less than querying the same data in CSV? > Athena bills by the amount of data scanned. Parquet is columnar, so a query only reads the specific columns it needs and skips the rest on disk. CSV is row-based, so the engine has to scan entire rows (all columns) even if the query only needs one or two fields — scanning more data means a higher bill.

6. When would you choose a provisioned warehouse (Redshift) over serverless querying (Athena), or vice versa? > Choose a provisioned warehouse for frequent, heavy, predictable workloads — the fixed cluster cost gets amortized across constant use, and query performance is more consistent. Choose serverless querying for occasional or exploratory queries — you avoid paying for a cluster that sits idle most of the time, even though each individual query might cost a bit more per-run than an already-running cluster would.
