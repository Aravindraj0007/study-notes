Stage 2.1 — Object Storage Deep Dive

Use cases for analytics

Recap from Module 1: Object storage (S3) holds files in a flat space, each with a unique key — not a traditional folder system.

Why analytics workloads specifically love object storage:

  • It's where raw data lands first (before it's processed into a warehouse or used by ML)
  • It's cheap enough to store everything — even data you might never query, "just in case"
  • Every other analytics tool in your syllabus (Athena, Glue, SageMaker, Spark) can read directly from it without you moving the data anywhere

Easy example: A hospital's analytics team dumps years of raw patient-visit logs into S3. They don't know yet which years or fields they'll need for a future study — object storage lets them keep everything cheaply until they do.

Performance and storage tiers

Not all data is accessed equally often, so object storage offers different "tiers" — same data, different price/speed trade-off.

Tier (AWS naming)Access speedCostUse case
Hot / StandardInstantHighestData accessed daily/weekly
Cool / Infrequent AccessInstant, small retrieval feeMediumData accessed monthly
Cold / ArchiveMinutes to hours to retrieveLowestOld data kept for compliance, rarely touched

Easy example: Think of your phone storage vs. a cloud backup vs. a dusty hard drive in a cupboard. Photos from this week (hot) you open instantly. Photos from 3 years ago (cold) you'd tolerate a slower retrieval for, because storing them cheaply matters more than speed.

Provider equivalence for tiers (good to know cold — exam loves asking "what's the Azure/GCP name for X"):

TierAWSAzureGCP
HotS3 StandardHot BlobStandard
CoolS3 Infrequent Access (S3-IA)Cool BlobNearline
Cold/ArchiveS3 GlacierArchive BlobColdline / Archive

Analyzing suitability of storage tiers for scenarios

This is a judgment skill, not a fact to memorize — the question is always "how often is this data accessed, and how fast do I need it back?"

ScenarioRight tierWhy
Live dashboard pulling today's salesHotNeeds instant access
Monthly compliance reportsCoolAccessed occasionally, some delay is fine
7-year-old financial records (legal requirement to keep)Cold/ArchiveAlmost never accessed, just needs to exist cheaply

Quick decision rule to use in exams: ask two questions — (1) how often is it read? (2) how fast do I need it back when I do read it? High frequency + fast → Hot. Low frequency + can tolerate delay → Cold. Anything in between → Cool.

Stage 2.2 — Building Data Lakes on the Cloud

Architecture patterns

Recap: A data lake = raw data stored cheaply (usually on S3), structured later when queried (schema-on-read).

A common real-world data lake isn't one giant messy pile — it's organized into layers, often called the medallion architecture (bronze/silver/gold — worth knowing even though your syllabus doesn't name it directly, since it's the standard pattern):

  • Raw/Bronze layer — data exactly as it arrived, untouched, unstructured
  • Cleaned/Silver layer — duplicates removed, formats fixed, still fairly raw
  • Curated/Gold layer — fully cleaned, aggregated, ready for a warehouse or dashboard

Easy example: Think of a messy garage (bronze) → sorted into labeled boxes (silver) → the specific box brought into the house because you need it right now (gold).

What this looks like as actual S3 folder structure (this is how it's done in practice, and a likely practical/exam scenario):

s3://company-datalake/
├── bronze/
│   └── orders/2026/08/07/orders_raw.json
├── silver/
│   └── orders/2026/08/07/orders_cleaned.parquet
└── gold/
    └── orders_daily_summary/2026/08/orders_summary.parquet

Notice: bronze keeps the raw format (JSON, as it arrived), silver/gold convert to Parquet once cleaned (ties into Stage 2.3 below) — this is a common exam "trace the pipeline" question.

Metadata management

Metadata = "data about the data." Not the actual file contents, but details like: when was it created, what format is it, what does each column mean, who owns it.

Why it matters: A lake with millions of raw files is useless if nobody knows what's inside each one. Metadata is what makes a lake searchable instead of just a dumping ground.

Easy example: A library with thousands of books but no catalog card system — you'd have to open every single book to find what you want. Metadata is the catalog card.

Concrete example of metadata for one file:

FieldValue
Fileorders_2026_08.parquet
Created2026-08-07
FormatParquet
Rows1,204,532
Columnsorder_id (int), customer_id (int), amount (float), order_date (date)
Ownerdata-eng team
SensitivityInternal — contains customer_id

Data catalog services

A data catalog is the actual tool/service that stores and manages all that metadata, and lets people (or other services) search "what data do we have, and where is it?"

Tool: AWS Glue Data Catalog (also used later for ETL in Module 4).

Easy example: Google Search for your company's data lake — you type "customer transactions 2023" and it tells you exactly which S3 folder/file has it, what columns it has, without you manually browsing.

How you'd actually create one (Glue Crawler via CLI) — a crawler is the tool that scans your S3 data and auto-populates the catalog:

aws glue create-crawler \
  --name orders-crawler \
  --role AWSGlueServiceRole \
  --database-name analytics_db \
  --targets '{"S3Targets": [{"Path": "s3://company-datalake/silver/orders/"}]}'

aws glue start-crawler --name orders-crawler

# after it finishes, check what schema it detected:
aws glue get-table --database-name analytics_db --name orders

Once this runs, the table orders becomes queryable by Athena (Module 3) directly — no manual schema definition needed.

Stage 2.3 — Storage Formats for Analytics

This is about how a file is physically structured on disk — it directly affects how fast you can query it later.

Row-based vs Column-based (the concept behind all 3 formats)

  • Row-based (like a CSV) stores each full record together — great for grabbing one entire row fast, bad for scanning just one column across millions of rows.
  • Column-based stores each column together — great for analytics, where you often want "just the sales column across all 10 million rows," not the whole record.

Easy example: Row-based is like a filing cabinet where each folder is one customer's full file. Column-based is like separate folders for "all phone numbers," "all emails," "all addresses" — if you only need everyone's email, you open one folder, not ten thousand.

Visual — same 3-row table, stored two ways:

Table:
| id | name  | amount |
|  1 | Asha  | 500    |
|  2 | Ravi  | 750    |
|  3 | Meera | 300    |

Row-based storage on disk (CSV-style):
[1,Asha,500] [2,Ravi,750] [3,Meera,300]
→ to read "amount" only, you still touch every full record.

Column-based storage on disk (Parquet-style):
id:     [1, 2, 3]
name:   [Asha, Ravi, Meera]
amount: [500, 750, 300]
→ to read "amount" only, you read ONE block: [500, 750, 300]. Skip id and name entirely.

Parquet

  • The most common analytics format. Column-based, compressed, widely supported (Athena, Redshift Spectrum, Spark, BigQuery all read it natively).
  • Easy example: If your syllabus's practical component has you "work with Parquet files," this is the format you'll actually convert a CSV into and query faster afterward.

Avro

  • Row-based, but still efficient — designed more for data that's being transferred/streamed (like between systems) rather than for analytical queries.
  • Easy example: Good for message queues/streaming pipelines (like Kafka, which you'll meet in Module 4) — you're moving whole records quickly, not scanning columns.

ORC (Optimized Row Columnar)

  • Also column-based like Parquet, developed originally for the Hadoop ecosystem (Hive). Very similar purpose to Parquet, slightly different internals — the exam-relevant point is just "another columnar analytics format," not that you need to know internal differences deeply.

Why columnar formats beat row-based formats for analytics

Three reasons, all connected:

  1. Faster queries — only read the columns you actually need, skip the rest
  2. Better compression — similar data (all numbers, all dates) sitting together compresses much better than mixed row data
  3. Lower cost — services like Athena charge by data scanned; scanning less data (because you skip unused columns) = cheaper queries

Quick comparison table:

FormatStructureBest for
CSVRow-based, uncompressedSimple, human-readable, but slow/expensive at scale
AvroRow-based, compressedStreaming/transferring whole records
ParquetColumn-based, compressedAnalytical queries (most common choice)
ORCColumn-based, compressedAnalytical queries (Hadoop/Hive ecosystem)

Stage 2.4 — Practical Component

What you should actually be able to do. Each item now has the actual command/code, not just the checkbox.

  • [ ] Upload/manage data in cloud object storage — create files/folders in an S3 bucket, delete/move objects

    • ``bash aws s3 mb s3://my-datalake-demo aws s3 cp orders.csv s3://my-datalake-demo/bronze/orders/ aws s3 mv s3://my-datalake-demo/bronze/orders/orders.csv \ s3://my-datalake-demo/bronze/orders/2026-08-07/orders.csv aws s3 rm s3://my-datalake-demo/bronze/orders/2026-08-07/orders.csv ``

  • [ ] Use CLI/SDK to interact with storage — e.g., AWS CLI aws s3 cp, or Python's boto3

    • ```python import boto3

s3 = boto3.client("s3")

# upload s3.upload_file("orders.csv", "my-datalake-demo", "bronze/orders/orders.csv")

# download s3.download_file("my-datalake-demo", "bronze/orders/orders.csv", "orders_local.csv")

# list what's in a "folder" (prefix) resp = s3.list_objects_v2(Bucket="my-datalake-demo", Prefix="bronze/orders/") for obj in resp.get("Contents", []): print(obj["Key"], obj["Size"]) ```

  • [ ] Work with Parquet files in a cloud context — convert a CSV to Parquet, upload it, notice the smaller file size

    • ```python import pandas as pd import boto3 import os

# read CSV, write as Parquet df = pd.read_csv("orders.csv") df.to_parquet("orders.parquet", engine="pyarrow", compression="snappy")

print("CSV size:", os.path.getsize("orders.csv"), "bytes") print("Parquet size:", os.path.getsize("orders.parquet"), "bytes") # Parquet is typically 4-10x smaller than CSV for the same data

# upload the Parquet version to the silver layer s3 = boto3.client("s3") s3.upload_file("orders.parquet", "my-datalake-demo", "silver/orders/orders.parquet") ```

  • [ ] Set up a basic data catalog crawler — point an AWS Glue crawler at your S3 data, let it auto-detect the schema and register it in the Glue Data Catalog

    • ```bash aws glue create-crawler \ --name my-orders-crawler \ --role AWSGlueServiceRole \ --database-name analytics_db \ --targets '{"S3Targets": [{"Path": "s3://my-datalake-demo/silver/orders/"}]}'

aws glue start-crawler --name my-orders-crawler

# verify: list tables the crawler created aws glue get-tables --database-name analytics_db `` Once cataloged, the table is immediately queryable via Athena — no manual CREATE TABLE` needed (you'll use this directly in Module 3).

Module 2 — Self-Test (with Answer Key)

Try answering first, then check.

1. Why do analytics teams prefer object storage over a regular database for raw incoming data? > It's cheap enough to store everything "just in case," doesn't require defining a schema upfront, and every analytics tool (Athena, Glue, Spark, SageMaker) can read directly from it without moving the data.

2. What's the difference between hot, cool, and cold storage tiers? > Hot = instant access, highest cost, for frequently accessed data. Cool = instant access with a small retrieval fee, medium cost, for occasionally accessed data. Cold/Archive = minutes-to-hours retrieval time, lowest cost, for rarely accessed data (e.g., compliance archives).

3. What does "metadata" mean, and why does a data lake need it? > Metadata is "data about the data" — creation date, format, column meaning, ownership, etc. Without it, a lake with millions of files is unsearchable; you'd have to open every file to know what's inside. A data catalog stores and makes this metadata searchable.

4. What's the difference between row-based and column-based storage? > Row-based stores each full record together (fast to fetch one whole row, wasteful to scan one column across millions of rows). Column-based stores each column together (fast to scan one column across all rows, since you skip unrelated columns entirely).

5. Name the 3 storage formats covered, and which one is most common for analytics. > Parquet, Avro, ORC. Parquet is the most common for analytics (column-based, compressed, universally supported). Avro is row-based and better suited to streaming/transferring whole records. ORC is column-based like Parquet, mainly used in the Hadoop/Hive ecosystem.

6. Why does scanning less data (via columnar formats) actually save money on cloud tools like Athena? > Athena bills by the amount of data scanned per query. Columnar formats let the engine read only the specific columns a query needs and skip the rest physically on disk — so a query that needs 2 of 20 columns scans roughly 1/10th the data of a row-based file, directly cutting the bill.
