Module 04 — Cloud Data Pipelines and Machine Learning

Study Notes (matches your tracker's Stage 4.1 – 4.5) — Enhanced Edition (Theory-Focused)

Stage 4.1 — Managed ETL/ELT Services

Recap from Module 1: ETL/ELT is the pipeline that moves data from source → destination while cleaning/transforming it. This stage is about the actual tools that run that pipeline for you on the cloud, instead of you writing and scheduling scripts by hand.

AWS Glue

  • A managed ETL service. You point it at a data source (like S3), it can auto-detect the schema (using the Glue Data Catalog from Module 2), and you write or generate a transformation job (Python/Spark under the hood) that cleans and moves the data.
  • Easy example: Like hiring a cleaning service that already knows your house's layout (the catalog) and just needs you to say "clean the kitchen and put dishes in the cupboard" (the transformation logic) — you don't manage the cleaning equipment yourself.
  • Worth noting why Glue is "managed": under the hood it's running Spark jobs (Module 1's Spark), but you never provision or size the cluster yourself — Glue allocates and tears down the compute automatically per job run. This is the same "managed" pattern as RDS in Module 1: the underlying engine is a familiar technology, the cloud service just hides the operational burden of running it.

Azure Data Factory

  • Azure's equivalent — a managed pipeline-orchestration and ETL service. Same job as Glue, Microsoft ecosystem, with a strong visual drag-and-drop pipeline builder.
  • Conceptually Data Factory sits closer to Airflow (below) than to Glue in one respect: it explicitly brands itself as an orchestration tool first, with transformation capability built in — whereas AWS keeps these as two cleanly separate services (Glue = transform, Airflow/Managed Workflows = orchestrate). Good to know if a question asks you to map Azure's single-service model onto AWS's two-service model.

Google Cloud Dataflow/Dataproc

  • Dataflow — GCP's managed service for both batch and streaming data processing (built on Apache Beam). The Beam foundation is the key differentiator: Beam is a unified programming model where you write one pipeline definition that can run in either batch or streaming mode — you don't rewrite the job depending on which pattern you need (contrast this with the Batch vs. Streaming tooling split described in Stage 4.4, where AWS/Azure generally use separate tools for each mode).
  • Dataproc — GCP's managed Hadoop/Spark cluster service (closer to "Spark-as-a-service", conceptually the GCP counterpart to AWS EMR from Module 1).
  • Both do the ETL/processing job, just GCP's flavor of it — but Dataflow leans toward the "fully managed, don't think about clusters" end of the spectrum, while Dataproc leans toward "managed cluster, but still a cluster you can configure," similar to the Glue-vs-EMR distinction on AWS.

Apache Airflow — visual pipeline orchestration

This is a different job from Glue/Data Factory — don't confuse them.

  • Glue/Data Factory do the actual data transformation.
  • Airflow orchestrates — it decides when and in what order different jobs run, and what happens if one fails. Think of it as the project manager, not the worker.

Core concept: DAG (Directed Acyclic Graph) — a pipeline in Airflow is defined as a sequence of steps with dependencies (e.g., "Step B can only start after Step A finishes successfully"), with no loops allowed (acyclic).

Why "acyclic" matters, not just "graph": if loops were allowed, a pipeline could reference its own earlier step and create infinite/ambiguous execution order — Airflow needs a guaranteed starting point and a guaranteed ending point to know the pipeline will actually terminate. This is the same underlying reason database transaction dependency graphs and build-tool dependency graphs (e.g., Makefiles) are also required to be acyclic — it's a general pattern in any dependency-based scheduling system, not something unique to Airflow.

Easy example: A recipe: "boil water → add pasta → drain → add sauce." Airflow is the person following that recipe in the right order, waiting for each step to finish before starting the next, and stopping/alerting if a step fails (e.g., pasta overflows). Glue/Data Factory would be the actual boiling and draining.

The orchestrator-vs-worker distinction, generalized: this same split — a tool that decides what/when vs. a tool that does the actual work — reappears throughout the module. Airflow orchestrates Glue jobs; Kafka (Stage 4.4) doesn't process data itself, it just carries it to tools that do; even a training job in SageMaker (Stage 4.3) is "orchestrated" by you submitting it, while the actual compute is elsewhere. Recognizing which role a service plays is a recurring exam distinction.

Stage 4.2 — Serverless Data Processing

Recap: "Serverless" (from Module 3's serverless querying) means you don't manage any server — you just provide code, it runs when triggered, and you pay only for the execution time.

AWS Lambda

  • Run a small piece of code (a "function") in response to a trigger — e.g., "whenever a new file lands in this S3 bucket, automatically run this cleaning script." No server to provision, no idle cost.
  • Easy example: Like a motion-sensor light — it does nothing until triggered (someone walks by / a file arrives), then runs briefly, then switches off. You don't pay for the light staying on all day.
  • Important architectural constraint worth knowing conceptually: Lambda functions are meant for short, lightweight tasks (historically capped at 15 minutes of runtime) — this is why Lambda is positioned as the "glue" connecting bigger services rather than doing the heavy transformation itself. A multi-hour Spark aggregation job belongs in Glue/EMR, not Lambda; Lambda is the trigger/dispatcher, not the workhorse.

Azure Functions

  • Azure's equivalent to Lambda — same trigger-based, pay-per-execution model.

Why this matters for pipelines: Lambda/Functions are often the small "glue" pieces connecting bigger services — e.g., a file lands in S3 → Lambda triggers → kicks off a Glue job or notifies Airflow.

How Stage 4.2 relates back to Stage 3.1's compute/storage separation: serverless functions are the same underlying idea (compute decoupled from any standing infrastructure) applied at the code execution layer instead of the query layer. Athena made "compute" mean "a transient query engine"; Lambda makes "compute" mean "a transient function execution." Same architectural principle, different layer of the stack — recognizing this pattern is useful if a question asks you to compare serverless concepts across modules.

Stage 4.3 — Managed ML Platforms

Recap from Module 1: ML Platforms let you train, deploy, and serve ML models without owning GPU hardware.

SageMaker (AWS) / Azure ML / Vertex AI (GCP)

All three do the same job — different provider, same purpose. Learn SageMaker's structure well (your syllabus's practical component is built around it) and treat Azure ML/Vertex AI as the same concept under a different name.

ML Platform features — notebooks, training jobs, endpoint deployment, AutoML

Break the ML lifecycle into 4 stages, matching what these platforms provide:

  1. Notebooks — a hosted coding environment (like Jupyter) where you explore data and write model code, without setting up Python/libraries locally.
  2. Training jobs — you submit your training code, SageMaker temporarily rents you a powerful (often GPU) machine just for the training duration, then releases it. You pay only for training time — same "rental" idea as EC2 Compute from Module 1.
  3. Endpoint deployment — once trained, the model gets hosted as a live API. Other applications send it data and get a prediction back in real time.
  4. AutoML — for when you don't want to manually choose/tune a model. You feed in labeled data, and the platform automatically tries multiple algorithms and picks the best-performing one.

Why these 4 stages are sequential, and why that sequence matters conceptually: each stage produces the input the next stage needs — a notebook produces a trained-model definition, a training job produces trained model weights/artifacts, an endpoint takes those artifacts and makes them callable. AutoML is really a shortcut that collapses "notebook exploration + training job" into one automated step when you don't want to hand-pick the algorithm — it still ends at the same endpoint-deployment stage as the manual path. Seeing AutoML as a shortcut through stages 1-2, rather than a separate 5th stage, is the more exam-accurate way to think about it.

Easy example — the full lifecycle: Swiggy's delivery-time prediction: a data scientist explores past delivery data in a notebook, submits a training job on that data, the trained model gets hosted as an endpoint, and the Swiggy app calls that endpoint every time you order to show "arriving in 24 mins."

A second worked example, to make sure the lifecycle generalizes beyond delivery times: A bank building a loan-default risk model. Notebook: a data scientist explores historical loan repayment data, tries a few feature combinations (income, credit history, loan amount). Training job: once a feature set looks promising, it's submitted as a formal training job on the full historical dataset — this run is logged with its accuracy metrics. Endpoint: the trained model is deployed as an API. Application use: the bank's loan-approval system calls that endpoint the moment a new application comes in, gets back a risk score, and uses it to approve/flag the application — all in real time, with no human re-running any code.

Applying ML services conceptually to a pipeline

The key insight for your syllabus: ML isn't standalone — it plugs into the same pipeline you've been learning all module.

Raw data (S3) → ETL/ELT (Glue/Data Factory, orchestrated by Airflow)
    → Cleaned data → ML Platform (train + deploy model)
    → Endpoint → Application uses the prediction

*Why ML has to come after ETL/ELT in this diagram, not before: models are only as good as the data they're trained on ("garbage in, garbage out"). Raw data (bronze layer, Module 2) usually has duplicates, missing values, and inconsistent formats — feeding that directly into a training job means the model learns from noise. The cleaned/curated data (silver or gold layer) is what actually gets used for feature engineering and training. This is also why Stage 4.1's orchestration (Airflow) typically has "run the Glue job" as a DAG step before* "trigger the SageMaker training job" — the dependency in the DAG mirrors this pipeline dependency exactly.

Stage 4.4 — Pipeline Architecture and Streaming

Pipeline Architecture Analysis — Batch vs. Streaming patterns

Batch processing — data is collected over a period of time, then processed all at once, on a schedule (e.g., every night at 2 AM, process yesterday's orders).

  • Tools involved: Glue, Data Factory, Spark, Airflow (scheduling the batch job)
  • Easy example: Doing all your laundry once a week, in one big load.

Streaming processing — data is processed continuously, the moment it arrives, with little to no delay.

  • Easy example: Washing each item of clothing the instant it gets dirty, one at a time, non-stop.

When to use which:

BatchStreaming
LatencyMinutes to hours acceptableSeconds or less required
Example use caseMonthly sales reportFraud detection on a live transaction
ComplexitySimpler to build/debugMore complex, needs careful handling of continuous data
Typical toolsGlue, Spark (batch mode), Airflow-scheduled jobsKafka, Spark Streaming, Lambda (event-triggered)

The underlying trade-off, stated as a general principle (this is the "Analyze"-level framing an exam question is likely testing): batch trades latency for simplicity and efficiency — processing in large chunks lets the system optimize/compress/dedupe across the whole batch at once, and failures are easy to reason about (just re-run the batch). Streaming trades simplicity for latency — you get near-instant results, but every event has to be handled individually and correctly the moment it arrives, with no natural "batch boundary" to fall back on if something goes wrong mid-stream. Neither is strictly better; the right choice depends entirely on how fresh the answer needs to be versus how much operational complexity you're willing to take on.

A subtlety worth knowing: "batch" and "streaming" describe processing pattern, not data source. The same raw data (e.g., order events) could be processed either way depending on business need — a batch job might run nightly over the same Kafka topic that a separate streaming consumer reads in real time. It's common to run both patterns off one source simultaneously (this is sometimes called a "lambda architecture" — not to be confused with AWS Lambda the service — though your syllabus doesn't require that specific term).

Introduction to real-time streaming — Apache Kafka

What Kafka actually is: A messaging system that lets data producers (apps, sensors, logs) publish a continuous stream of events, and consumers (other services) read that stream in real time, independently and at their own pace.

Core concepts:

  • Producer — something that sends data into Kafka (e.g., a food-delivery app sending "order placed" events)
  • Topic — a named channel/category the data flows through (e.g., a topic called "orders")
  • Consumer — something that reads data from a topic (e.g., a service updating a live dashboard)

Why Kafka needs to decouple producers from consumers, conceptually: without something like Kafka in between, the order-placing app would need to know directly about every downstream system that cares about new orders (a dashboard, a fraud-check service, an inventory system) and call each one individually — if a new consumer is added later, the producer's code has to change too. Kafka inverts this: the producer only knows about the topic, and any number of consumers can independently start reading from it, present or future, without the producer ever being modified. This decoupling is the actual architectural reason streaming systems use a message broker instead of direct service-to-service calls.

Easy example: Kafka is like a live news ticker. Reporters (producers) post updates continuously to a channel (topic). Anyone watching (consumers) — a TV channel, a website, a mobile app — reads the same live feed independently, at their own pace, without the reporter needing to know who's watching.

Why it connects to Batch vs. Streaming above: Kafka is the backbone that enables streaming architecture — it's literally the pipe that carries continuous data, which downstream tools (like Spark Streaming) then process in real time. Kafka itself doesn't do any processing/transformation — it's pure transport, which ties back to the orchestrator-vs-worker distinction from Stage 4.1: Kafka is neither the orchestrator nor the worker, it's the pipe connecting them.
