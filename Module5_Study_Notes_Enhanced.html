Stage 5.1 — Cloud Visualization

Power BI — cloud integration

Recap from Module 1: Visualization tools turn raw query results into charts a non-technical person can understand.

How Power BI actually works with the cloud: Power BI doesn't store your data itself — it connects live to your data source (a warehouse like Redshift/Synapse/BigQuery, or even a data lake via serverless querying). Power BI sends a query behind the scenes, gets results back, and renders them as a chart.

Easy example: Think of Power BI as a TV screen and your cloud warehouse as the cable box. The TV doesn't store the show — it just displays whatever the cable box is currently sending. If the warehouse data updates, the "channel" (dashboard) can refresh to show the new picture.

Why this "TV/cable box" separation matters conceptually: it means Power BI inherits all of the architectural trade-offs from whichever backend it's pointed at. A Power BI dashboard built on Redshift behaves like a provisioned-warehouse consumer (fast, consistent, but the cluster has to be running and billing). The same dashboard pointed at Athena/BigQuery instead behaves like a serverless-query consumer (no idle cost, but each refresh triggers a fresh pay-per-query cost). Power BI itself doesn't change the underlying cost/performance model from Module 3 — it just sits on top of it. This is a common way exam questions link Module 5 back to Module 3.

Connecting Power BI to cloud data sources

The connection is essentially the same pattern every time:

  1. Power BI needs credentials/permissions to access the warehouse (this is where Stage 5.3's IAM comes in — Power BI needs an IAM role/user with read access)
  2. You pick the specific database/table (or write a custom SQL query) as the data source
  3. Power BI can either import the data (takes a snapshot, faster to explore but goes stale) or use DirectQuery (always live, but every interaction re-queries the warehouse)

Easy example — Import vs DirectQuery: Import is like taking a photo of a scoreboard — fast to look at anytime, but it's frozen at that moment. DirectQuery is like watching the live scoreboard through a window — always current, but you depend on the window (connection) staying open.

The underlying trade-off, generalized: this is the exact same fixed-cost-vs-variable-cost, freshness-vs-speed pattern that shows up repeatedly across the syllabus — Import behaves like a batch snapshot (Module 4's batch processing, cheap and fast to interact with, but stale until the next refresh); DirectQuery behaves like streaming/live access (always current, but every single interaction re-incurs the underlying query's cost and latency). Recognizing "Import vs DirectQuery" as another instance of the batch-vs-streaming trade-off, rather than a Power-BI-specific quirk, is the kind of connection an "Analyze"-level exam question rewards.

A second consideration DirectQuery introduces that Import doesn't: because DirectQuery re-queries the warehouse on every user interaction (every filter click, every drill-down), a dashboard with many simultaneous viewers can generate a large, unpredictable number of warehouse queries — directly inflating cost on a serverless backend, or straining concurrency limits on a provisioned cluster. Import avoids this entirely since the data is already sitting locally in Power BI once loaded.

Creating dashboards

A dashboard is just multiple charts/visuals arranged together, usually built from one or more datasets connected as above. The core skill isn't Power BI's buttons — it's picking the right chart for the right question (covered in the Practical section below: bar, line, pie).

Stage 5.2 — Cost Management and Optimization

Pricing models

Cloud services generally bill you in a few recurring patterns — recognizing which applies to a service tells you how to control its cost:

Pricing modelHow it worksExample from earlier modules
Pay-per-use / on-demandCharged for exact resource-time usedEC2 running by the hour (Module 1)
Pay-per-query / data scannedCharged based on how much data a query touchesAthena, BigQuery (Module 3)
Reserved/committedPay upfront or commit to usage for a discountReserved EC2 instances for predictable workloads
Storage tier-basedCharged differently based on access frequencyS3 hot/cool/cold tiers (Module 2)

Why this matters here: cost isn't one uniform bill — every service you've learned about across Modules 1–4 has its own pricing logic, and optimizing cost means understanding which logic applies to which piece of your pipeline.

A framing that ties all four models together: every pricing model in this table is really answering the same underlying question — "what is the unit the provider is metering?" On-demand meters time the resource exists. Pay-per-query meters data touched. Reserved meters a commitment, trading flexibility for a lower rate. Storage tiers meter how often you access, not how much you store. Once you can name the metering unit for any service in the syllabus, you can predict its cost behavior without memorizing the service individually — e.g., you already know Lambda (Module 4) must be pay-per-use metered by execution time, because "serverless" as a category always meters actual usage, never idle existence.

Monitoring costs

Cloud providers give you dashboards/tools to see exactly where money is going, broken down by service, team, or project — before the bill surprises you at month-end. Tool: AWS Cost Explorer.

Easy example: Like a bank app's "spending by category" screen — instead of just seeing one total bill, you see "₹X went to groceries, ₹Y went to fuel," letting you spot what's actually driving the cost.

Why monitoring has to be a separate discipline from pricing models themselves: knowing how a service bills (pricing model) doesn't tell you how much of it you're actually using across a whole organization, where dozens of teams might be spinning up EC2 instances, Athena queries, and S3 buckets independently. Monitoring is the feedback loop that turns the abstract pricing model into an actionable number — without it, cost optimization (below) has nothing concrete to act on.

Tagging strategy

Tags are labels (key-value pairs, e.g., project: cloud-analytics, team: data-eng) attached to cloud resources (an EC2 instance, an S3 bucket) so costs can be tracked and filtered by who/what they belong to.

Easy example: Like writing your name on your lunchbox in a shared office fridge — without a tag, nobody (including you) can tell whose usage is whose when the bill arrives.

Why tagging is the mechanism that makes monitoring actually useful at scale: Cost Explorer can show you "total S3 spend this month," but without tags it can't tell you which project or team that spend belongs to — the bill is one undifferentiated number. Tags are what let a cost-monitoring tool break a single aggregate bill down into meaningful, attributable slices. This is the same underlying need as metadata in a data lake (Module 2) — untagged resources are to a cloud bill what unmetadata'd files are to a data lake: technically present, but not attributable or searchable.

Cost optimization strategies

Common, practical moves — most of which you've already learned the mechanism for in earlier modules:

  • Right-sizing compute — don't rent a huge EC2 instance if a small one handles the load (Module 1)
  • Using the correct storage tier — move rarely-accessed data to cold storage (Module 2)
  • Scanning less data — use Parquet + partitioning so Athena/BigQuery bill less (Module 2 & 3)
  • Turning off idle resources — stopping a dev/test EC2 instance overnight instead of leaving it running
  • Using serverless where workload is unpredictable — pay only when actually used (Module 3 & 4's Lambda/Athena)

The single principle underneath all five strategies: every one of these is really "match the resource's cost-shape to your actual usage pattern" — right-sizing matches capacity to load, storage tiers match cost to access frequency, scanning less matches spend to query need, turning off idle resources removes cost during zero usage, and serverless removes the fixed-cost mismatch entirely for unpredictable workloads. None of these are independent tricks to memorize separately; they're the same optimization lens (from Module 3's fixed-vs-variable-cost discussion) applied to five different services.

Evaluating cost-effectiveness of a solution

This is a judgment skill: given two architectures that both technically work, which one costs less for the actual usage pattern?

Easy example: A provisioned Redshift cluster running 24/7 makes sense if queries happen constantly all day. But if your team only runs reports once a week, that same cluster sitting idle most of the time is far more expensive than just using Athena (serverless, pay-per-query) instead — same data, same eventual answer, very different cost.

How to structure this judgment for an exam answer: identify (1) the usage frequency/predictability of the workload, (2) which pricing model each candidate architecture uses (fixed vs. variable, from the framing above), and (3) whether the workload's frequency sits above or below the rough break-even point between the two. This is the same break-even logic introduced in Module 3 for Redshift vs. Athena — Module 5.2 is really asking you to apply that logic as a general skill, not just for warehousing specifically.

Stage 5.3 — Security and Governance

IAM policies

IAM = Identity and Access Management. It answers one question: "Who is allowed to do what?"

  • A user/role is an identity (a person, or a service like Power BI/Lambda)
  • A policy is a document that says exactly what that identity can and can't do (e.g., "can read from this S3 bucket, cannot delete anything")

Easy example: Like a hotel keycard system. Your keycard (IAM role) is programmed to open your room and the gym, but not the manager's office or other guests' rooms (the policy). Reception can issue different keycards with different access, without changing the locks themselves.

Why it's been relevant this whole course: Every practical task you've done — Power BI connecting to a warehouse (5.1), a Lambda function reading from S3 (Module 4), a Glue crawler scanning a bucket (Module 2) — needed an IAM role/policy behind the scenes to be allowed to act.

The conceptual reason IAM has to sit "underneath" every other service rather than being one more service among many: every architectural pattern covered so far — compute/storage separation, serverless functions, orchestration, streaming — assumes that services are constantly calling other services on your behalf (Lambda reading S3, Airflow triggering Glue, Power BI querying Redshift). None of that inter-service communication works unless something is answering "is this caller allowed to do this?" at every single hop. IAM isn't a feature bolted onto the pipeline; it's the trust layer the entire pipeline architecture depends on to function at all.

Encryption

Data is scrambled so it's unreadable without the correct key — protects data even if someone gains unauthorized access to the raw storage.

Two states worth knowing:

  • Encryption at rest — data is encrypted while stored (e.g., an S3 bucket's files)
  • Encryption in transit — data is encrypted while moving over the network (e.g., between your laptop and the cloud)

Easy example: At rest = a locked safe (even if someone breaks into the room, they can't open the safe without the key). In transit = a sealed envelope in the mail (even if someone intercepts it, they can't read the letter inside without opening it — encryption is like tamper-proof sealing).

Why both states are needed, not just one: encryption at rest alone doesn't help if an attacker intercepts data as it travels between your S3 bucket and, say, a Glue job reading from it — the data is decrypted in transit unless that channel is separately protected. Encryption in transit alone doesn't help if an attacker gains direct access to the storage disk itself while data sits idle. The two protect against two entirely different attack surfaces (network interception vs. storage compromise), which is why "is data encrypted" as an exam/checklist question always needs to be answered for both states separately, not as one yes/no.

Network security — VPC, Security Groups

VPC (Virtual Private Cloud) — your own isolated, private network within the cloud provider's infrastructure. Resources inside it (like an EC2 instance or RDS database) aren't exposed to the public internet by default.

Security Groups — act like a firewall attached to a specific resource, controlling exactly which traffic (which IP addresses, which ports) is allowed in or out.

Easy example: A VPC is like a gated residential society — only people who belong inside can access it by default. A Security Group is like the individual lock on your specific apartment door within that society — even someone inside the gate still can't get into your apartment unless your door's rules allow them.

Why two layers (VPC + Security Group) instead of just one: a single layer of protection means one misconfiguration exposes everything. Two independent layers mean an attacker has to defeat both the perimeter (VPC) and the resource-level control (Security Group) — this "defense in depth" idea (multiple independent layers, each capable of stopping an attack on its own) is a general security principle, not something specific to cloud networking, and it's the same reasoning behind requiring IAM policies and encryption and network controls all at once rather than relying on any single protection.

Compliance considerations

Certain industries (healthcare, finance) have legal requirements about how data must be stored, encrypted, and who can access it (e.g., patient data regulations). Cloud providers offer compliance certifications and tools, but the responsibility to configure things correctly (right encryption, right access policies) is still yours — this is often called the shared responsibility model: the provider secures the underlying cloud infrastructure, you secure how you configure and use it.

Where the dividing line actually falls, conceptually: the provider is responsible for things you have no visibility or control over at all (physical data center security, the hardware, the hypervisor). You're responsible for everything you configure — which IAM policies you write, whether you turned on encryption, whether your S3 bucket is public, how you set up your VPC. A useful mental test: if a setting has a toggle/switch you could have flipped, it's your responsibility; if it's below the layer you can even see, it's the provider's. This is why "the cloud is secure" is a misleading half-truth — the infrastructure being secure doesn't protect you from your own misconfiguration, which is consistently the actual cause of most real-world cloud data breaches (an exposed S3 bucket or overly broad IAM policy, not a flaw in AWS/Azure/GCP itself).

Evaluating security posture

A judgment skill: given a cloud architecture, can you spot security gaps? Common things to check:

  • Is sensitive data encrypted (at rest and in transit)?
  • Are IAM policies following least privilege (giving only the minimum access needed, nothing more)?
  • Is anything unintentionally exposed to the public internet that shouldn't be (e.g., an S3 bucket, a database)?

Why "least privilege" specifically, rather than just "restricted access": the point isn't merely that access should be limited — it's that every identity should have the minimum access that lets it do its actual job, no more. The reasoning is damage containment: if a Lambda function's credentials are ever compromised, least privilege means the blast radius is limited to exactly what that function legitimately needed (e.g., read access to one S3 prefix) rather than broad access to the entire account. This connects directly back to the IAM keycard example — the hotel doesn't give every guest a master key "just in case," even though it would be more convenient, because a lost keycard should only ever risk one room.

Stage 5.4 — Holistic Evaluation

Evaluating Solutions Holistically — performance, scale, cost, security, governance trade-offs

This is where the entire course comes together — real cloud architecture decisions are never about picking "the best" tool in isolation; they're about trade-offs between competing priorities:

PriorityPulls you toward...Trade-off
PerformanceProvisioned warehouse (Redshift), hot storage tierCosts more, needs more management
CostServerless (Athena), cold storage, right-sizingCan be slower, less predictable performance
ScaleMPP architecture, compute/storage separationMore complexity to configure well
SecurityStrict IAM, encryption everywhere, private VPCCan slow down development, adds setup overhead
GovernanceData catalogs, tagging, compliance checksTakes upfront time/discipline to maintain

Easy example — putting it together: A startup's analytics team choosing between Redshift (provisioned) and Athena (serverless) isn't just a technical choice — it's really asking: do we query often enough that a standing warehouse is worth the fixed cost, or is our usage occasional enough that pay-per-query wins? That single decision touches performance, cost, and scale all at once — exactly the kind of question this module is training you to answer.

Why this table is genuinely the capstone of the whole syllabus, not just Module 5's topic: every row in this table is a callback to a specific mechanism you already learned in an earlier module — Performance = MPP/columnar storage (Module 3), Cost = the fixed-vs-variable metering framing (Module 5.2, built on Module 3's break-even logic), Scale = compute/storage separation (Module 3), Security = IAM/encryption/VPC (Module 5.3), Governance = data catalogs and metadata (Module 2). Holistic evaluation isn't new content — it's the skill of recognizing which of the last four modules' mechanisms is relevant to a given scenario, and weighing them against each other explicitly.

Exam framing: If asked to "evaluate a cloud architecture holistically," structure your answer around these 5 angles explicitly — most Bloom's "Analyze" level questions (which is what your syllabus's CO4/CO5 target) are really asking you to walk through this exact table.

Module 5 — Self-Test (with Answer Key)

Try answering first, then check.

1. What's the difference between Import and DirectQuery in Power BI? > Import takes a snapshot of the data into Power BI — fast to explore, but it goes stale until manually refreshed. DirectQuery always queries the live warehouse for every interaction — always current, but slower and dependent on the connection staying open, and every interaction re-incurs the underlying query's cost.

2. Name 3 different cloud pricing models and give one example service for each. > Pay-per-use/on-demand (EC2, billed by the hour); Pay-per-query/data scanned (Athena/BigQuery, billed by data touched); Reserved/committed (reserved EC2 instances, discounted for a usage commitment). (Storage tier-based, e.g. S3 hot/cool/cold, is a valid 4th answer too.)

3. What's the difference between what a VPC controls and what a Security Group controls? > A VPC is an isolated private network — it controls whether resources are exposed to the public internet at all (the perimeter). A Security Group is a firewall attached to a specific resource within that VPC — it controls exactly which traffic (IPs, ports) is allowed in/out of that individual resource (the door lock inside the gate).

4. What is the "shared responsibility model" in cloud security? > The cloud provider is responsible for securing the underlying infrastructure (physical data centers, hardware, hypervisor) — things you can't see or configure. You're responsible for how you configure and use the services on top of it (IAM policies, encryption settings, whether a bucket is public). Most real-world breaches come from misconfiguration on the customer's side, not a flaw in the provider's infrastructure.

5. What is the principle of "least privilege" in IAM? > Giving an identity (user or service) only the minimum access it needs to do its job, and nothing more. This limits the "blast radius" if that identity's credentials are ever compromised — e.g., a Lambda function should only get read access to the one S3 prefix it actually needs, not broad account-wide access.

6. Given a scenario with frequent, heavy analytical queries vs. one with rare, occasional queries — which warehouse approach (provisioned vs. serverless) fits each, and why? > Frequent, heavy queries → a provisioned warehouse (Redshift) — the fixed cluster cost gets amortized across constant, predictable use, and performance stays consistent. Rare, occasional queries → serverless querying (Athena) — no idle cost when nobody's querying, and occasional per-query charges end up cheaper overall than paying for a mostly-idle standing cluster. This is the same fixed-cost-vs-variable-cost break-even logic from Module 3, applied here as the general evaluation skill.
